FOR MANUS / BUILDER

GOAL
PrimeContractorOS is not just a dashboard. It is a complete guided operating system for government contractors, prime contractors, subcontractor coordination, proposal work, contract execution, finance tracking, compliance support, document management, and closeout.

Do not remove existing pages, sidebar groups, modules, cards, routes, or structure unless something is a broken duplicate.
Do not change the design unless required for mobile usability, accessibility, or broken layout fixes.
Keep what already exists and make it work fully.

Every page must answer:
1. What is this page for?
2. When should the user use it?
3. What can the user do here?
4. What happens after each action?
5. What records are created, updated, linked, or flagged?
6. What page should the user go to next?
7. What alerts, tasks, audit logs, or status changes happen in the background?

The system must follow this lifecycle:
Public Website / Signup
→ Onboarding
→ Dashboard
→ Opportunity
→ Proposal
→ Contract
→ Contract Hub
→ Active Operations
→ Finance
→ Closeout
→ Lessons Learned
→ Reports / Reuse / Templates

There are three major layers:
1. Public entry layer
2. Customer workspace layer
3. Platform admin / owner layer

PrimeContractorOS must remain:
- company/workspace-first
- government-contracting specific
- AI review-first
- source-aware
- action/result-driven
- platform-owner controls separate from customer workspace controls

============================================================
GLOBAL SYSTEM RULES
============================================================

1. Keep what already exists.
Do not delete existing sidebar items, modules, cards, or structure unless they are broken duplicates.

2. Every sidebar item must open a real page.
No blank pages. No placeholder-only pages. If a feature is not complete yet, show a working page with status, explanation, basic records, and next actions.

3. Every major page must include:
- Page title
- Plain-language page purpose
- “What this page is for”
- “When to use this page”
- “What to do next”
- Status summary cards
- Search/filter controls where useful
- Main table or card directory
- Add/create button where useful
- Detail view
- Edit/update ability
- Status fields
- Related records
- Alerts/tasks
- Empty-state guidance

4. Every action must have a visible result.
If user clicks Save, Create, Upload, Approve, Review, Archive, Assign, Send, Match, Convert, Generate, or Run Check, the system must show:
- success/failure message
- what changed
- where the record went
- what next action is recommended

5. Every important change must be logged.
Create audit/activity records for:
- created records
- edited records
- status changes
- deleted/archived records
- AI runs
- admin overrides
- billing changes
- user login events
- document generation
- file uploads
- approval/review actions
- plan changes
- support ticket changes

6. Alerts and tasks must be core execution tools.
Alerts = something needs attention.
Tasks = something needs action.
Alerts should be dismissible or convertible into tasks.
Tasks should have:
- owner
- due date
- priority
- status
- related record
- notes
- created source

7. AI must be review-first.
AI may suggest, summarize, extract, compare, and generate drafts.
AI must not automatically make legal/compliance conclusions final.
AI findings must show:
- source file
- source location if available
- category
- confidence/review status
- practical meaning
- action buttons:
  - Approve
  - Hold
  - Edit
  - Mark Needs Review
  - Create Task
  - Link to Contract Object

8. Government contracting rules must be treated as guidance support, not legal advice.
The app should track:
- SAM / UEI / CAGE
- NAICS
- solicitation source files
- set-aside awareness
- subcontracting / flowdown review
- governing contract files
- modifications
- invoice support
- payment tracking
- closeout blockers
- evidence

9. Awarded contract files become governing truth.
Proposal-stage assumptions must carry forward as history, but they must not become final contract obligations unless reviewed against the awarded contract or modification.

10. Invoices and payments must be separate.
Invoice = what was billed.
Payment = money actually received.
They can be linked/matched, but they are not the same record.

11. The system must be useful for new contractors and experienced contractors.
Every complex page must have beginner-friendly guidance without hiding advanced functionality.

12. Every record should connect to the workspace.
All customer-side records must belong to a workspace.

13. Platform Admin pages must be separated from customer workspace pages.
Platform Admin is for Reed’s Solutions / PrimeContractorOS owner controls.
Customer App is for customer operations.

REQUIRED FINAL RESULT
============================================================

When complete, the app should feel like this:

1. A public visitor understands what PrimeContractorOS is.
2. A new user can create a workspace.
3. The system routes them correctly after login.
4. Onboarding collects useful government contracting business data.
5. Dashboard tells the user what to do next.
6. Opportunities can convert to proposals.
7. Proposals can convert to contracts.
8. Contracts have a real Contract Hub.
9. AI confirmation is source-linked and review-first.
10. Requirements, deliverables, deadlines, and compliance items become live contract objects only after review.
11. Files, contacts, messages, subcontractors, vendors, invoices, and payments connect to records.
12. Finance separates invoices from payments.
13. Closeout checks blockers before closure.
14. Lessons feed templates and improvement.
15. Platform Admin controls workspaces, users, plans, billing, support, discounts, onboarding, activity, login events, and overrides.
16. Diagnostics and consistency pages help find broken setup/data.
17. Every action gives a result.
18. Every important result updates records, status, alerts, tasks, or audit logs.
19. Nothing important is just visual.
20. Do not change the current design style unless needed for mobile usability or accessibility.

FINAL INSTRUCTION
Audit the existing app first.
Keep the existing UI and navigation.
Then wire every route, page, button, form, card, table, status, record relationship, and result.
Do not leave placeholder pages.
Do not make buttons that do nothing.
Do not make AI final without review.
Do not merge invoices and payments.
Do not mix Platform Admin controls with Customer App controls.
